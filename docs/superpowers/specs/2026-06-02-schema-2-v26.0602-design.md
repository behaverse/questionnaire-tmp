# Schema 2 v26.0602 Authoring Spec (OD-16 Pivot)

**Date drafted:** 2026-06-02
**Author:** OD-16 resolution committee (grilling session 2026-06-02)
**Predecessor:** Schema 2 v26.0601 (tag `v26.0601`, commit `e9f5fd8` and follow-ups through `ad74a5a`)
**Severity:** `breaking`
**Authoritative scoring model:** [design/05b_scoring.md](../../../design/05b_scoring.md)

This spec describes the Schema 2 changes that land the OD-16 resolution. v26.0601's entity model (OD-15) is **preserved** for the 11 reusable entities and the page composition. What changes is the **scoring surface**: a new procedural entity (`Scorer`), a new top-level `scores[]` list, and the dissolution of `ScoringDef` / `InterpretationBand` / `Subscale.prompt_ids` / `Subscale.weight_per_prompt`.

The diff is small in entity count but **breaking in semantics**: instances written against v26.0601's scoring shapes will not validate against v26.0602, and migration is a one-shot author-driven operation. Hence the new CalVer.

## 2 — Conventions (unchanged from v26.0601 unless noted)

- **JSON Schema:** Draft 2020-12; `$schema` and `$id` at v26.0602.
- **`additionalProperties: false`** everywhere on project-owned objects; per-entity `extensions: {}` + `^x_` patternProperties for forward-compatible widening.
- **Identifiers:** unchanged for existing entities; **new** ID prefixes added:
  - `scr_` — Scorer
- **`scl_` prefix:** continues to denote Subscale; the entity's shape narrows (see §5.2).
- **CalVer in IDs and refs:** all references continue to be hard-pinned per OD-06 (`scr_phq9@v26.0602`).
- **Language map:** `content.{lang}` shape unchanged (per-language `{status, …translatable fields}` blocks).

## 3 — Top-level Questionnaire structure

The root-object diff from v26.0601 is concentrated in three properties:

| Property | v26.0601 | v26.0602 | Notes |
|---|---|---|---|
| `subscales` | required (could be empty) | **removed** | Subscale membership moves to `Prompt.subscales[]`. Subscale entities themselves still exist in the Library — they're just not enumerated at the Questionnaire level. |
| `scoring` | array of `ScoringDef` | **removed** | Replaced by `scores`. |
| `validation` | array of `CrossQuestionValidationRule` | unchanged | Cross-question validation is not scoring. |
| `scores` | — | **NEW**: array of `Score` declarations | Each entry is `{id, scorer, path, name?, description?}`. References JSON Pointer paths into a Scorer's structured output. |
| `lock_show_score_timing` | — | **NEW**: boolean, default `false` | When `true`, deployments cannot override the canonical show-score timing (per OD-16 §4.4). |

The root shape becomes:

```jsonc
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "@context": "https://behaverse.org/schemas/questionnaire/v26.0602/context.jsonld",

  "metadata":   { /* Schema 1 v26.0528 — unchanged */ },
  "style":      { /* unchanged */ },
  "flow":       { /* unchanged */ },
  "pages":      [ /* unchanged */ ],
  "blocks":     [ /* unchanged, optional */ ],

  "scores":     [ /* NEW — Score declarations referencing Scorer outputs */ ],
  "logic":      [ /* unchanged */ ],
  "validation": [ /* unchanged — CrossQuestionValidationRule[] */ ],

  "lock_show_score_timing": false,  /* NEW — optional, default false */

  "extensions": { /* unchanged */ }
}
```

`pages` remains required and non-empty; `metadata` remains required. `scores`, `logic`, `validation` are arrays (may be empty). `blocks` and `extensions` remain optional.

## 4 — New $def: Scorer

Lives in `$defs.Scorer`. Represents a versioned scoring procedure as a Library entity. Its instances are stored either as Library JSON documents (Library-resident, `scr_*@vYY.MMDD`) or — uncommonly — inline at the use site. The Schema 2 v26.0602 examples in §10 are Library-resident.

**Required fields:** `id`, `content`, `inputs`, `output_schema`, `implementations`, `test_cases`.

```jsonc
{
  "$id": "#/$defs/Scorer",
  "type": "object",
  "required": ["id", "content", "inputs", "output_schema", "implementations", "test_cases"],
  "properties": {
    "id": {
      "type": "string",
      "pattern": "^scr_[a-z0-9_]+$"
    },
    "name": {
      "type": "string"
    },
    "content": {
      "$ref": "#/$defs/ContentLanguageMap",
      "description": "Translatable description fields (e.g., name, description, methodology notes) per language."
    },
    "inputs": {
      "type": "object",
      "description": "JSON Schema describing the expected input object. Conventional top-level fields: responses, scored_responses, participant, deployment.",
      "properties": {
        "type":       { "const": "object" },
        "properties": { "type": "object" },
        "required":   { "type": "array", "items": { "type": "string" } }
      },
      "required": ["type"],
      "additionalProperties": true
    },
    "output_schema": {
      "type": "object",
      "description": "JSON Schema describing the structured output the scorer produces. The Questionnaire's scores[] entries reference JSON Pointer paths into this schema.",
      "properties": {
        "type":       { "const": "object" },
        "properties": { "type": "object" }
      },
      "required": ["type"],
      "additionalProperties": true
    },
    "implementations": {
      "type": "array",
      "minItems": 1,
      "items": { "$ref": "#/$defs/ScorerImplementation" }
    },
    "test_cases": {
      "type": "array",
      "minItems": 1,
      "items": { "$ref": "#/$defs/ScorerTestCase" }
    },
    "license": {
      "type": "string",
      "description": "Optional licence tag per design/11_content_licensing.md. Scorer licence may differ from Questionnaire licence."
    },
    "extensions": { "type": "object" }
  },
  "additionalProperties": false,
  "patternProperties": {
    "^x_": {}
  }
}
```

### 4.2 `ScorerTestCase`

```jsonc
{
  "$id": "#/$defs/ScorerTestCase",
  "type": "object",
  "required": ["input", "expected"],
```

## 5 — Modified $defs

### 5.1 Prompt — gains `subscales[]`

`$defs.Prompt.properties` adds:

```jsonc
"subscales": {
  "type": "array",
  "items": {
    "type": "string",
    "pattern": "^scl_[a-z0-9_]+(@v\\d{2}\\.\\d{4})?$"
  },
  "uniqueItems": true,
  "description": "Multi-valued list of Subscale ids this Prompt belongs to. Items routinely load on multiple subscales; this field encodes that. Per OD-16 4.5 (option P)."
}
```

Optional, not required. The `@vYY.MMDD` version suffix is optional only inside the same Library; cross-Library references must be version-pinned per OD-06.

### 5.2 Subscale — narrowed to label entity

```jsonc
{
  "$id": "#/$defs/Subscale",
  "type": "object",
  "required": ["id", "content"],
  "properties": {
    "id": {
      "type": "string",
      "pattern": "^scl_[a-z0-9_]+$"
    },
    "name":        { "type": "string" },
    "description": { "type": "string" },
    "content":     { "$ref": "#/$defs/ContentLanguageMap" },
    "extensions":  { "type": "object" }
  },
  "additionalProperties": false,
  "patternProperties": {
    "^x_": {}
  }
}
```

**Removed fields** vs. v26.0601: `prompt_ids`, `weight_per_prompt`, `translations`.

### 5.3 ScoringDef — removed

The entity is **gone**. There is no `$defs.ScoringDef`. Migration: each v26.0601 `ScoringDef` becomes one or more `Score` declarations referencing a Scorer entity that encodes the prior formula's logic.

### 5.4 InterpretationBand — removed

The entity is **gone**. There is no `$defs.InterpretationBand`. Migration: bands move inside the Scorer's output schema (e.g., `output_schema.properties.band: {min, max, label}` or `output_schema.properties.severity: enum`).

## 6 — New top-level type: `Score`

Lives in `$defs.Score`. Used inside the Questionnaire's `scores[]` array.

```jsonc
{
  "$id": "#/$defs/Score",
  "type": "object",
  "required": ["id", "scorer", "path"],
  "properties": {
    "id": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9_]*$",
      "description": "Local id used by LogicRule.condition and display layers. Need not carry a Library prefix."
    },
    "scorer": {
      "type": "string",
      "pattern": "^scr_[a-z0-9_]+@v\\d{2}\\.\\d{4}$",
      "description": "CalVer-pinned reference to a Scorer Library entity."
    },
    "path": {
      "type": "string",
      "pattern": "^(/[^/]*)+$",
      "description": "JSON Pointer (RFC 6901) into the Scorer's output_schema. Empty pointer (the whole output) is not allowed; scores must reference a leaf value."
    },
    "name":        { "type": "string" },
    "description": { "type": "string" }
  },
  "additionalProperties": false,
  "patternProperties": {
    "^x_": {}
  }
}
```

**Validation gates** (Library publish-time, not schema-level):
- The `scorer` ref must resolve to a published Scorer in the Library.
- The `path` must resolve against the Scorer's `output_schema` to a defined leaf field.
- The resolved leaf's type informs LogicRule type-checking at publish time.

These gates are *not* expressible in JSON Schema and are enforced by the validator (§11), not by `schema.json`.

## 7 — `pages`, `blocks`, `logic`, `validation`, `metadata` (unchanged)

No changes from v26.0601 except as noted:

- `pages[]` and `blocks[]` shapes are identical.
- `logic[]` `LogicRule` shape is identical; `LogicRule.condition` *semantics* gain support for score-id references (e.g., `score("phq9_severity") == "severe"`), but the **schema shape** is unchanged — the condition is still a string, and the WASM evaluator OD-11 contract widens to recognise score ids. That widening is documented in 05b_scoring.md §4.5 and does not require Schema 2 schema changes.
- `validation[]` `CrossQuestionValidationRule` shape is identical.
- `metadata` continues to embed Schema 1 v26.0528 via `$ref` to `https://behaverse.org/schemas/instrument/v26.0528/schema.json` (no Schema 1 bump).

## 11 — Validator updates

`tools/validate_schemas.py` already walks `library_examples/` per the v26.0601 implementation (Task 22). Extensions for v26.0602:

1. **`LIBRARY_ENTITY_DIRS` updates:** add `"subscales": "Subscale"` and `"scorers": "Scorer"` to the mapping. Each `library_examples/subscales/*.json` validates against `$defs.Subscale`; each `library_examples/scorers/*.json` validates against `$defs.Scorer`.

2. **New cross-reference checker `check_score_paths(root)`:** for each questionnaire example, for each entry in `scores[]`, attempt to resolve `scorer` against the published Scorer entries in `library_examples/scorers/`, then walk the JSON Pointer `path` against the Scorer's `output_schema`. Report:
   - `UNRESOLVED_SCORER` — the `scorer` id+version doesn't match any known Scorer entity.
   - `PATH_NOT_FOUND` — the path doesn't resolve to a leaf in the Scorer's `output_schema`.
   - `PATH_NOT_LEAF` — the path resolves but to a non-leaf (object/array root).

   This is the "publish-time validation gate" promised in §6.

3. **Optional: `check_scorer_conformance(root)`:** for each Scorer entity, run every `test_cases[]` through every implementation listed in `implementations[]`. This is *expensive* — requires WASM runtimes, HTTP clients, Python imports — so the v26.0602 validator includes only a **skeleton stub** that reports `SKIPPED` for each test case with a `not yet implemented` reason. The full check is a future deliverable (separate plan).

4. **No change** to the Schema 1 instrument validation logic.

Prepend the v26.0602 entry:

```markdown
## [v26.0602] — 2026-06-02

### Changed (severity: breaking — per OD-16 resolved 2026-06-02)

- **Scoring runtime semantics pivoted to external Scorer entity.** Schema 2 no longer carries an in-JSON formula language for scoring. A new procedural Library entity `Scorer` (`scr_*`) owns the procedure; the Questionnaire declares scores by id via `scores[]: { id, scorer, path, name?, description? }` referencing JSON Pointer paths into the Scorer's structured output.
- **`ScoringDef` removed** — replaced by `scores[]` entries referencing a Scorer.
- **`InterpretationBand` removed** — bands live inside the Scorer's `output_schema`.
- **`Subscale` shape narrowed** — entity now carries only `id`, `name`, `description`, `content`. `prompt_ids` and `weight_per_prompt` removed.
- **Subscale membership moved to the Prompt** — `Prompt.subscales: string[]` (multi-valued, references `scl_*` ids).
- **Questionnaire's top-level `subscales[]` block removed** — Subscale entities still exist in the Library; the Questionnaire just doesn't enumerate them.
- **New top-level `scores[]`** — array of `Score` entries.
- **New top-level `lock_show_score_timing: boolean`** — default `false`; when `true`, deployments cannot override the canonical show-score timing per OD-16 §4.4.
- **Cross-schema `$ref` to Schema 1 v26.0528 unchanged.**

### Added
- `$defs.Scorer` — versioned scoring procedure with inputs schema, output schema, implementations (WASM/HTTP/Python/R), and test cases.
- `$defs.ScorerImplementation` — implementation reference with `kind` discriminator.
- `$defs.ScorerTestCase` — input/expected pair for conformance testing.
```

## 16 — Open implementation questions (for the plan phase)

The following are *implementation* choices, not design choices. They surface during plan writing or task execution.

- **Path format:** strict JSON Pointer (RFC 6901, leading `/`) is mandatory. Confirm the spec's regex matches RFC 6901 exactly, including escape sequences (`~0` / `~1`).
- **Scorer entity inlining:** v26.0602 examples store Scorers as Library-resident files. Should the schema also permit a Scorer inline inside the Questionnaire JSON (parallel to Items being either Library or inline)? Recommendation: **no, for v26.0602**. Scorers are heavy (input schema, output schema, implementations, test cases); inline-only Scorers would clutter the Questionnaire. Defer inline support to a future bump if anyone asks.
- **`check_scorer_conformance` integration:** the validator stub returns `SKIPPED`. Wiring it to real WASM/HTTP/Python runtimes is out of scope for v26.0602; it's a follow-on deliverable.
- **`Prompt.subscales` migration tooling:** the legacy `survey_database` import gains a small adapter that walks the legacy `subscales` table and emits `Prompt.subscales[]` entries. Out of scope for the schema itself; relevant to the importer (see design/13_importers.md).
- **`Score.id` uniqueness:** must be unique within a Questionnaire. The schema can express this only via `uniqueItems` over a derived list; the validator enforces it as a post-pass check.
